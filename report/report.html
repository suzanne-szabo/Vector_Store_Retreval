1. Task and Corpus

The agent answers questions from a fixed corpus of PDFs. It searches a persistent Chroma vector store, answers only from the passages it retrieved, cites each passage by chunk id, source and page, and reports “insufficient evidence” when the corpus does not support an answer. The application, not the model, validates every tool call and citation, counts steps, and decides how each run ends.

I chose Python and RISC-V assembly instead of the supplied FDA food-safety corpus because I plan to build a personalized programming tutor for my senior research project. Building this assignment on that subject let me test the whole retrieval process (ingestion, hybrid search, a bounded ReAct agent and citation checks) on the kind of material the tutor will need, and see whether such an agent responds well when a student asks about a Python or assembly assignment. The instructor approved a different topic provided the nine required queries mirror the supplied pattern; each of my queries keeps the question type of its counterpart in the supplied set (Section 5).

Like the supplied corpus, mine mixes authoritative, earlier-edition, tutorial and reference sources, so the agent has to use source roles and versions correctly. The corpus has nine PDFs, 2,017 pages and 5,655 chunks. The PDFs are not in the repository; corpus/sources.toml records each file’s download URL, license and SHA-256 hash, and ingestion refuses a file whose hash does not match.

2. Design

I acted as orchestrator and architect: I chose the corpus, approved every design decision (D1–D25 in specs/architecture.md), ran the services and required runs, and checked the results. Following my HW-08 process, specifications came first, then black-box tests written from them, then code (Section 7 describes the AI assistance).

2.1 Vector store

  • Extraction and cleaning: pdfplumber in layout mode (x_tolerance=1, with per-column extraction for the two-column Guo paper), Unicode NFKC normalization, removal of repeated running headers and footers, dot leaders and private-use glyphs, and vocabulary-aware rejoining of words hyphenated across lines.
  • Chunking: 1,000-character chunks with 150-character overlap. Chunks never cross pages, so every chunk has exactly one page.
  • Metadata: each chunk stores its source id, title, file name, subject, version, file SHA-256, one-based physical PDF page, character offset and a stable chunk id: the first 24 hex digits of SHA-256 over the source file hash, page, offset and text. Rebuilding with the same settings gives the same ids.
  • Embedding and store: Qwen3-Embedding-8B (4,096 dimensions) through the course gateway; one persistent Chroma collection with cosine distance. uv run python -m rag_agent.ingest --rebuild rebuilds it (about 22 minutes), and a manifest records the settings and an index_version. Ingestion refuses to mix different chunk or cleaning settings in one store.
  • Hybrid retrieval: vector search alone missed some passages that exact technical words find (for example, the limitations section of the Guo paper never reached its top 10). Each search therefore fuses a vector list and a BM25 keyword list (30 candidates each) with Reciprocal Rank Fusion (k = 60). Queries are embedded with the Qwen3 instruction “Given a question, retrieve passages that answer it.” On a 24-case retrieval probe, this combination put the answering passage first in 16 cases and in the top 5 in 21, with a worst rank of 8, better than vector, keyword or plain hybrid alone.

2.2 Tools

Both tools have typed Pydantic argument schemas; unknown fields, wrong types and out-of-range values are rejected before anything runs.

  • search_documents(query, sources?, subject?, k?) returns up to k ranked passages (default 5, maximum 8), each with its chunk id, source id, title, one-based page and text. Filters by source id or subject let the model target a specific document.
  • finish(outcome, answer, citations) ends the run with answer or insufficient_evidence. Each citation gives a marker number n, a chunk id and what it supports; the answer text uses [n] markers. Limits: 8,000 characters and 12 citations.

2.3 Controller and loop

The loop is a LangGraph graph (START → llm → controller → tool → continue? → llm or END). The chat model (Qwen3.8-Flash-Next) must make exactly one tool call per turn. The controller applies seven policies in order: a run already ended (P1), an unknown tool (P2), invalid arguments or an unknown source (P3), finish before any search (P4), a citation whose chunk was not retrieved in this run (P5), citation-marker rules (P6: every citation used once and every marker matched), and more than one call in a reply (P7). A rejection is returned to the model as an observation it can correct. Every run ends with exactly one terminal reason, checked in this order:

  • ANSWER or INSUFFICIENT_EVIDENCE: an accepted finish;
  • ERROR, with a kind: MODEL_ERROR, RETRIEVAL_ERROR, NO_ACTION (a reply with no tool call, after one reminder) or REJECTION_LIMIT (three consecutive rejections);
  • STEP_LIMIT: the configured number of model/tool steps (8) is used up.

Each run writes a JSON Lines trace: a header with the question, configuration and manifest, one entry per step (the tool, its arguments, whether it was accepted, the policy and reason for a rejection, and the observation), and the final result with its terminal reason, answer and resolved citations.

2.4 Source attribution

Attribution is checked in two layers. Provenance is checked by code: a citation is valid only if its chunk id was returned by search_documents earlier in the same run (P5), and the final citations are resolved to source, title and page from those retrieval results, not from the model. Support, whether each claim follows from its cited passage, cannot be checked that way, so I evaluated it claim by claim (Section 5.3). The system prompt also gives the role of every source, tells the model to prefer the 2025 manual over the 2019 edition for current rules, and to quote exact values from passages.

5.2 What went wrong, and what I changed

Run 1 (runs/2026-10-27_1914/) met 7 of 9. In both misses, retrieval had found the right passages; the failure was in producing the final answer:

  • Q3, ERROR/NO_ACTION: the model wrote a complete cited answer as plain text instead of calling finish, and the controller ended the run at once.
  • Q6, STEP_LIMIT: its answers were 5,865 and then 4,308 characters, over the 4,000-character limit, and the rejection did not say by how much.

Both came from limits I had set without evidence, so I changed them for all queries rather than for these two: the answer limit became 8,000 characters and the rejection now states the length (D23); a reply without a tool call gets one reminder before NO_ACTION (D24); and the prompt states the citation limit (D25). Specifications and failing tests were updated before the code. I then reran all nine with one configuration. Q3 passed. Q6 failed again, differently: six of its eight steps went to searching; the first finish added a field the citation schema does not allow, and the second listed 13 citations, one over the limit.

I stopped after run 2. A third round aimed only at Q6 would have tuned the system to one query. The failure was also safe: the controller accepted no malformed answer, so the run ended with no answer rather than an unchecked one. In an uncounted check run made between runs 1 and 2 (runs/not-required/check-fixes/), Q6 did end with an accepted answer on its last step, citing all three required sources. The question is answerable, but not reliably within 8 steps.

6. Observed Limitations

  • Provenance is not support. The citation check proves a passage was retrieved, not that it says what the claim says. The unsupported additions in Section 5.3 passed every automated check and were found only by reading the passages.
  • Cross-document questions need more steps. A question spanning three sources spent about six of eight steps searching, leaving two attempts to produce a valid finish. Future work: accept and ignore harmless extra citation fields, warn the model when two steps remain, and give multi-source questions a larger step budget.
  • Behavior varies between runs. Even at temperature 0, the same Q6 question failed three different ways across three runs, so one run per query is a small sample.
  • Limits can trade away support. Enforcing the 12-citation limit made the model drop a citation while keeping the claim it supported.
  • Extraction is imperfect. Some words broken across lines are not rejoined, a few page layouts jumble example output, and the Winans draft’s margin line numbers remain in its chunks.
  • Retrieval needed both methods. Vector search alone missed exact technical passages, and keyword search alone missed questions phrased differently from the text. A question asked word for word still ranked its passage only 7th.
  • Model constraints. The assigned chat model was unavailable to my key, so the results come from Qwen3.8-Flash-Next.

What this means for the tutor

The agent handled single-source questions a student might ask, such as what an instruction does, why an indentation error happens or what an operator computes, and it refused honestly when the corpus could not answer. The specifications answer “what is the rule” well but are not tutorials, so a tutor would need more worked examples. Questions that join Python and assembly were the hardest, and those are the ones my tutor most needs. A tutor would also need a support check, not just a provenance check, before showing an answer to a student.
